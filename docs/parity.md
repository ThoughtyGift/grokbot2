# Parity — what the local app still lacks

Measured against the original running side by side (`--user-data-dir` + separate CDP port, see
`HANDOFF.md` §3), plus the descriptors and prompts extracted from the shipped bundles.

Method note: the box gateway is called from the **main process**, so renderer network capture
shows nothing (`capture-box.mjs` and the first `diff-capabilities.mjs` both came back empty for
this reason). The usable probes are the rendered DOM (`scripts/diff-capabilities.mjs`), the
extracted tool catalog, and the extracted base system prompt.

## 2. Attachments — DONE, and harder than it looked

`chat.ts` used to declare `TextMsg.images?: string[]`. Nothing assigned it and the renderer has
no such path, so no screenshot could ever reach the transcript. Replaced with the real contract,
which took six tested variants in the live app to pin down. **Three gates, all undocumented:**

1. **The media gate is the URL string's file extension — nothing else.** `AZ(url)` splits on
   `/` and `\`, takes the last segment, reads after the last `.`. A base64 `data:` URL has no
   dot, so it renders as a *file chip* no matter what `file_name` says. (`data:…#shot.png`
   passes the gate but then fails to resolve.)
2. **The desktop rejects Windows drive paths.** `normalizeAttachmentSource` runs
   `new URL(source)`; `C:…` parses with protocol `c:` and is dropped. A `file://` URL is
   worse — it throws inside the message renderer and takes the whole section down.
3. **A non-URL path is passed through**: tried against the desktop's own filesystem first, then
   handed to the box gateway as `readAttachmentImage({path}) → {dataUrl, width, height}`.
   Omit `width`/`height` and you get "Image unavailable".

So: `src/attachments.ts` hands out virtual paths (`/workspace/attachments/N-name.png`) and serves
the bytes through the new gateway method; images are written to `.data/attachments/` so they
survive a backend restart (in memory only, every screenshot went "Image unavailable" after a
tsx reload). Browser tools now attach a screenshot after **every** action, which is what the
original's own browser-use reminder says it does.

Verified in the running app: a staged screenshot renders inline at 1920x953.
Regression test: `scripts/e2e-attachment.mjs`.

## 2b. `ask_question` — DONE

The client's own zod schema, lifted from the widget view chunk (`view-CG_6Qsxm.js`), including
its wording:

```
Option = { label, value?, description?, style?: default|primary|danger }
          value: "Text sent back to you when this option is picked. Defaults to the label."
Widget = { prompt, helpText?, options: 1..6, allowCustom?, dismissOnMoveOn? }
```

Two things the schema does not tell you, and both matter:

- `respondedValue` / `widgetDismissed` live on the **entry**, not inside `message.widget`. That
  is what flips the card from question to answered (client: `HWn`).
- `respondToWidget` is declared `reply: "record-or-null"` — returning `{}` is wrong; it returns
  the updated entry. The real payload is `{entryId, value, agentId}`, read off the wire with
  `GROKBOT2_LOG=1` because the call site could not be resolved statically.

Also fixed while here: `isAutoApproved` was exported from `tools.ts` and **never called**, so
every read-only tool still put an approval card in front of the user. `injectTool` now honours
it, and a question is auto-approved — otherwise you click Allow to be asked something.

Verified in the app: the model called `ask_question`, four options rendered, clicking one
flipped the card to the answered state with a tick and echoed the answer as a user turn.

## 2c. The original system prompt — PORTED

`buildSandBaseSystemPrompt` is 179 chapters / 59 KB in the box host bundle. We keep **56 of
them, ~19 KB (~4.9k tokens)**, generated by `scripts/build-prompt.mjs` into `src/prompt-base.ts`.

**This had to be a port, not a copy, because one thing is inverted:**

| | original | ours |
|---|---|---|
| plain assistant text | a private scratchpad the user never sees | **is** the visible message |
| how a reply reaches the user | the `SendMessage` tool, its "only voice" | streamed straight into the bubble |

Copying the "SendMessage is your only voice" chapter verbatim would have taught the model to
write inner monologue into the user's chat and to call a tool that does not exist. That whole
chapter is dropped and every remaining mention is rewritten to plain "reply".

Dropped whole, rather than half-adapted, because the model cannot call them: cloud agents,
`Task` subagents, connectors, plugins/MCP management, Cursor Origin, threaded replies,
ExternalShell. A prompt describing a tool that does not exist is worse than silence about it.

Added: a Language chapter. The original is English-only — it has a "mirror the user" rule for
tone but none for language, so without it the ported prompt answers Vietnamese in English.

Observable difference on the same question ("what can you do?"):

- before — "Mình là trợ lý ảo… có thể hỗ trợ bạn nhiều việc như:" + a four-bullet feature list
- after — "Mình là Grok Bot, trợ lý desktop giúp bạn xử lý công việc… Cần hỗ trợ gì cứ ới mình nhé!"

The bullet list is exactly what the original prompt forbids ("Prose, not outlines").
`GROKBOT2_PROMPT=short` restores the old one when latency matters more than voice.

## 2d. Box handoff — the VNC sign-in flow

**The FE is identical in both apps — it is the same signed binary.** The original shows a
sign-in handoff card and ours did not, purely because our backend never emitted one. Nothing
was missing on the client side.

The contract, from the client: `status.handoff = { instruction, requestId, snapshotDataUrl? }`
on the forever-box status. The renderer turns it into a **"Needs your attention"** card with the
instruction and two buttons — *Skip this step* and *I'm done, continue* — plus a snapshot frame
(`aria-label="Take over the computer"`) that only appears when `snapshotDataUrl` is supplied.
*I'm done, continue* calls `handBackForeverBox({id, trigger})`.

Implemented as `request_box_help` (the original's tool name) in `forever-box.ts`: the tool
returns a promise that stays pending until hand-back, so the agent's turn genuinely waits.

Why this shape and not "ask the user for the password": the original is explicit —
*"You never ask for, see, or type their password or 2FA; they authenticate on the box desktop,
and the session persists there, so it is a one-time step."*

Verified end to end in the app: agent asks → card renders → click *I'm done, continue* →
handoff clears → the same turn resumes with "Cảm ơn bạn! Mình thấy bạn đã đăng nhập xong…".

Note: chapters 106-115 of the original prompt (*Reaching services that have no connector*)
describe exactly this flow and were dropped from the port in §2c because they named surfaces we
lacked. Now that `request_box_help` and subagents exist, they are worth re-adding.

## 2e. Parked turns — one persistence path instead of four

Four separate in-memory maps each orphaned their own card on restart: the approval `pending`
map, `widgetHistory`, and box `handoffs`/`resumers` (attachments had already been moved to
disk for the same reason). The symptom was always the same and always looked like a broken
contract — the card stayed on screen, clicking it did nothing.

They turned out to be one thing in three costumes: **the turn stops, a card sits on screen, and
when the user acts the model resumes from `history`**. So they are now a single `Parked` record
persisted in `state.json`:

```ts
{ kind: "approval" | "widget" | "handoff", key, agentId, history, entryId?, toolCallId?, name?, arg? }
```

One thing genuinely cannot be persisted: the Promise a waiting tool is awaiting. `requestBoxHelp`
returns one, and it dies with the process. So hand-back takes two routes — resolve the Promise
when the turn is still in flight, or re-enter the model loop from the stored history when it is
not (`setHandBackSink`). The parked copy is dropped on the live path so a later restart cannot
replay a handoff the user already finished.

Fixed alongside: `reqSeq`/`toolSeq` restarted at 1 every boot while `entrySeq` was derived from
disk, so successive runs reissued `req-1`. Two live approvals could key the same entry, and
resolving one could run the other's tool. Both are now derived from what is already persisted.

Verified: an approval card created **before** a restart, approved **after** it — the tool ran,
the card went `approved`, and the turn continued from the persisted history.

## 2g. The box desktop and its browser — DONE

plank + google-chrome + thunar + xfce4-terminal**, replacing fluxbox + xterm.

Host: `103.75.186.63`, **SSH port 24700** (found in `Quản lÝ manager/.deploy.local.json`).

## 2h. MCP — DONE

`get_mcp_tools` and `call_mcp_tool` over stdio JSON-RPC, against servers declared in a
repo-root `.mcp.json` — the same shape Claude Code and Cursor use, so an existing config drops
straight in. Servers start lazily on first use and are reused (`npx -y <server>` costs seconds).
Only offered to the model when at least one server is declared.

Verified against `@modelcontextprotocol/server-memory`: handshake, `tools/list` (9 tools), a
real `create_entities` → `search_nodes` round-trip, plus the failure paths — unknown tool and
malformed args both answer clearly instead of hanging.

**That config file holds live tokens**, so nothing about a server is ever logged except its
name: not `env`, not `args`, and its stderr is drained without printing. Learned the hard way —
dumping one such file into a transcript is how two working credentials got exposed.

## 2j. Keeping the box tunnel up

`infra/scripts/box-tunnel.ps1` holds `127.0.0.1:9223` pointed at the box's Chrome DevTools and
redials when the link drops. `-Install` puts a shim in the per-user **Startup folder**;
`-Uninstall` removes it.

Startup folder rather than a scheduled task on purpose: `schtasks /sc onlogon` returns
"Access is denied" without elevation, and this needs none. Same effect at logon, nothing
system-wide.

Host and key come from `.env` (`GROKBOT2_BOX_SSH=root@HOST:PORT`, `GROKBOT2_BOX_SSH_KEY`), so
nothing about the box is committed.

Verified by killing it: ssh pid 31652 -> 17800, and the port answered Chrome/149 again. A
dropped tunnel otherwise presents to the agent as "no page target", which reads as a broken
backend rather than a dead link.

Two things this cost, both worth remembering:

- **`.ps1` must be ASCII** unless it has a BOM. Windows PowerShell 5.1 reads it as ANSI, so one
  em dash in a comment broke the parser at load.
- The first version **printed "Installed" after `schtasks` had failed**, because the exit code
  was never checked. It now verifies the port answers and says so either way.

## 2k. Regression I introduced: the box browser kept jumping to Google

Symptom the user hit: the box's Chrome would reload itself and land back on google.com,
throwing away whatever page was open, with Chrome icons piling up in the dock.

Cause was §2g's own fix. `Restart=always` plus a **startup URL** meant every exit relaunched
Chrome *at that URL*. And Chrome exits on its own routinely — it relaunches to apply an update
(the "New Chrome available" prompt was visible in the screenshots the whole time). systemd saw
the main process exit, started a second Chrome, and the cycle repeated: `NRestarts=4` within
the hour.

Three changes:

- `Restart=on-failure`, not `always`. Restart a crash; do not fight a deliberate or
  self-managed exit by racing a duplicate against it.
- **No startup URL** — `about:blank`. The agent decides what to open, so a relaunch must never
  reopen a page over its work.
- `--disable-component-update --disable-background-networking --no-service-autorun`, because
  Chrome's own updater is what was making it exit.

After: `Restart=on-failure`, `NRestarts=0`, **one** Chrome instance (10 OS processes is just
Chrome's multi-process architecture), CDP answering, and `e2e-browser.mjs` still passes.

The general lesson, since this is the second time it bit: a supervisor that restarts a process
must not re-apply *initial* state on restart. `Restart=always` on something that legitimately
self-restarts turns one process into two.

## 2l. Drafts, checklist and plan

`email_draft` / `slack_draft` emit the client's own draft cards; `todo_write` / `todo_read` /
`create_plan` keep a per-agent checklist (persisted, so a restart mid-task keeps the plan).
Field names are the client's: `draft.to/subject/body` and `draft.workspace/target/thread/body`.

**Correction to an earlier reading.** I first reported drafts as display-only, because grepping
for `sendDraft` / `draftAction` / `respondToDraft` found nothing. The screenshot says otherwise:
both cards render with a **"Ready to send"** pill and working **Send / Discard** buttons. The
component takes `{draft, status, onSend, onDiscard}` and `status` has `sending` and `sent`
states. Absence of a guessed name is not absence of a feature — the handler simply lives in a
lazily-loaded chunk under a different one.

**Resolved — there is no method.** The earlier search failed because it assumed one existed.
The draft cards live in their own lazily-loaded chunks (`view-DdBVyaYO.js` for Slack,
`view-VJCKZMro.js` for email), and each ends the same way:

```js
onDiscard: zs, onSend: Ss, status: q     // passed into the card
function Ss(){}                          // onSend
function zs(){}                          // onDiscard
```

Both handlers are empty, and neither identifier is assigned anywhere else in its chunk
(`grep 'Ss='` / `'zs='` return nothing). The Send and Discard buttons render, they are
clickable, and clicking them does nothing in this build.

The half that *is* wired runs the other way: `status` comes from `entry.draftSendState`
(`entry.draftSendState ?? "editable"`, values `editable | sending | sent`), and in the whole
renderer `draftSendState` appears exactly once — inside the memo cache-key builder. The client
only ever **reads** it. So the state is the backend's to drive, and there is no round trip to
implement.

Our behaviour therefore already matches the original: the cards render, nothing can be sent,
and the tools say so. Note this is *not* "unfinished on our side" — it is unfinished upstream.

## 2m. Bot-to-bot messaging — DONE

`message_agent({"to":…,"content":…})`. The renderer needs nothing new: a `kind:"message"`
entry carrying `toAgent` renders as "Messaged <name>" on the sender's side, and one carrying
`fromAgent` renders as "Message from <name>" on the recipient's. Both come from the client's
own `ide` switch, which treats `role:"user" && fromAgent != null` as an assistant-side entry
rather than a user bubble.

Two things worth keeping:

* **One entry, not two.** The first version pushed the inbound entry itself *and* called
  `sendPrompt` with a `[từ bot X] …` prefix, so the recipient saw the message twice. The
  attribution now travels as a `fromAgent` field on `SendArgs`; the "[tin nhắn từ bot X]"
  prefix is added only when building the model's history, never to the stored text.
* **A hop counter** (`MAX_HOPS = 3`) stops two bots answering each other forever. It is keyed
  on the receiving agent, so a chain A→B→C→… is what runs out, not one bot's own budget.

## 2n. Writing files, and attaching one — DONE

Names are the catalog's, not invented: `edit_file_v2` (whole-file write, from
`EditFileV2Params.contents_after_edit`), `edit_file` (targeted, from `old_string`/`new_string`)
and `delete_file`. All three require approval; the read-only tools do not. They are backed by
the daemon's `write` / `replace` / `remove` ops, which were written earlier but had never been
deployed — the box was still running a build whose op list ended at `grep`.

**A latent bug this surfaced.** `parts()` called `unquote()` on the whole argument before
splitting it. For one argument that is harmless; for two it is not, because `"a.md", "text"`
begins and ends with a quote, so the outer pair came off and the path became `a.md"`. The box
really did end up with a file named `bao-cao.md"`, trailing quote included. Each part is now
unquoted individually. `glob_file_search(<pattern>, <dir>)` had the same defect and nobody had
noticed.

Contents also arrive through a `name(arg)` call rather than JSON, so a model writing markdown
types `\n` and means a newline. The file tools accept a JSON object (preferred — it survives
content containing commas) and unescape `\n`/`\t`/`\"` in the positional form.

**Attaching a non-image.** The renderer's `qvn` routes a `type:"attachment"` message by
extension alone: an http(s) url with no `file_name` is a link, a known image extension is an
image, everything else is a **file chip**. So `attach_file` posts the same message shape as a
screenshot with the box path as `url`. Opening the chip calls two gateway methods, and main.cjs
forwards both to the box rather than answering them locally:

```
readAttachmentText({path})                   -> null | {kind:"binary", bytes}
                                                    | {kind:"text", text, truncated, bytes}
readAttachmentChunk({path, offset, length})  -> {totalSize, bytesBase64}    length:0 = probe
```

`bytes` is the file **size**, not its content — that is where the chip's "6.9 KB" comes from
(client `Eft`: one decimal under 10 KB). Returning the text there would render a nonsense size
and no error at all.

**The bug that hid all of it.** The gateway dispatcher did `val = fn(args)` with no `await`.
Every handler had been synchronous, so nobody had needed it; the two attachment readers are the
first async ones, and `JSON.stringify(Promise)` is `{}`. A 200 with an empty body is
indistinguishable from a method that legitimately returns nothing — the same "handled ≠ read
correctly" class as every other entry in this document. The dispatcher now resolves promises.

## 2o. The tunnel loop that never dialed

`box-tunnel.ps1` skipped a cycle whenever *anything* held the local port ("do not fight a manual
tunnel") and wrote nothing to its log until ssh exited. With a manual `ssh -L` already running,
that meant an empty log file and a loop that neither dialed nor explained itself — it read as
hung. The evidence that settled it was the absence of the log, not a guess about ssh.

It now decides on a CDP probe instead of on whether the port is bound, because a half-dead ssh
keeps a socket bound while forwarding nothing, and reports which of three states it is in
whenever that changes: `up` (answers, whoever owns it), `blocked` (bound, no answer — needs a
human), `dialing`. `-Status` prints the same in one line. Verified by killing the manual tunnel:
detected and redialed in 19s.

## 2p. `getSubagents` — shape resolved, and implemented

`getSubagents({id}) → array`, where `id` is the **parent** agent. The host builds it in one
place, so the shape is not a guess:

```js
function listSubagents() {
  return [...subagentRegistry.entries()].map(([subagentId, record]) => ({
    subagentId, subagentType: record.subagentType, title: record.title,
    status: record.status, startedAtMs: record.startedAtMs
  })).sort((a, b) => a.startedAtMs - b.startedAtMs);
}
```

Two traps in the details:

* **`status` is `running | done | aborted | error`.** Grepping for status strings near the
  registry turns up `completed`, but that is the *outcome*'s vocabulary — the host translates
  on the way in: `outcome.status === "completed" ? "done" : "error"`. Storing "completed"
  would render a row the client has no state for.
* **`subagentType` is a free string**, taken from the task's own `subagent_type`, not an enum.
  Our `browserUse` / `explore` / `shell` belong there unchanged.

There is a push channel too: `ingestSubagentsEvent({parentAgentId, subagents})`.

Implemented against that: `task_v2` registers a row before dispatching (a list that only gains
a row when the work *finishes* never shows anything running) and settles it after. Verified end
to end — `running` while the subagent worked, `done` after, and empty for every other bot.

Worth recording about the test itself: the first two attempts showed an empty list and looked
like a bug in the new code. Neither had run a subagent. The model answered a trivial "list the
workspace" by calling `list_dir_v2` directly instead of delegating, and the second attempt sat
in `task_v2`'s approval card. Read the tool **name** in the transcript before concluding
anything from an empty list.

var CONNECTOR_MANIFESTS = [

`connectGuide` is empty for both, and the agent-facing text ends with "Coming soon (not

## 2r. Side-by-side E2E, and the two gaps it found

Both instances open at once (local on CDP 9222, the original on 9333 with its own
`--user-data-dir`), then compare the rendered DOM rather than the method table. Two things that
every API-level test had passed turned out to be visibly wrong.

### The sidebar had no second line

The original's rows read `name / time / last message`; ours read only the name. The row
component takes both from the **agent summary**, not from the transcript:

```js
m = put(t.lastEntry)     // preview text
h = l5e(t.updatedAt)     // "9:03 AM" | "Yesterday" | weekday | date
```

so a record without them renders a name and two blanks — which is what we shipped.

```
updatedAt : ms. `l5e` returns "" for 0 or missing, hence no timestamp at all.
lastEntry : {kind:"text", text}
          | {kind:"attachment", count, kinds:[{kind, count}]}
          | {kind:"link", url}
```

The attachment branch is where **"Sent 1 Markdown file"** comes from: the client pluralises
`kinds` itself against a fixed table — image · video · audio · pdf · markdown · table · json ·
text · document · archive · file — and anything outside it degrades to "file". A MIME type or a
bare extension there reads "1 file" with no error. Tool echoes are skipped when picking the
preview, or the sidebar shows raw JSON arguments where the reply belongs.

Verified in the running app: `ChipTest2 · 9:11 AM · Sent 1 Markdown file`, and the file chip
renders `ghi-chu.md / 31 B` with the same icon and download button as the original's
`cinai-14day-calendar.md / 6.9 KB`.

### The transcript showed its own plumbing

Ours put two things in the bubble column that the original never shows:

* `🔧 name({"json":"args"}) → result` after every tool, and

## 2s. One tool per turn — the cap that made multi-step flows impossible

The follow-up prompt after a tool said *"không gọi công cụ nữa"*. A turn could therefore run
exactly one tool: the agent opened a page and stopped. The original chains from a single
message — navigate, screenshot, narrate, click, screenshot, hand the box over — so no flow with
more than one step could be reproduced, however good the individual tools were.

Now bounded at `MAX_TOOL_STEPS = 8` per user message, reset on each new prompt. Bounded rather
than open-ended because each step is a full model round trip and a model that misreads a result
would otherwise retry forever; on the last step the instruction reverts to "answer now", so a
turn always ends in a reply instead of a silent stop.

Verified against the original's own flow: `browser_navigate` → screenshot attached →
`browser_take_screenshot` → screenshot attached → `request_box_help`, ending with the
"Needs your attention" card and its *Skip this step* / *I'm done, continue* buttons.

Two fixes fell out of running it:

* **Browser actions no longer ask for approval.** They were falling through to the permission
  card because they are registered directly into the chat tool map and never had a
  `needsApproval: false` spec. The original asks for nothing here — a sign-in flow there runs
  navigate → screenshot → click in one breath — and the user is watching the box's own Chrome
  live in the VNC pane. Anything that writes to disk still asks.
* **`request_box_help` printed raw JSON.** The model sent `{"message": "…"}`; we read
  `instruction` / `prompt` and fell back to the raw argument, so `{"message":"…"}` appeared in
  the chat as if it were a sentence. It now reads any of the usual keys, and failing that any
  single string value in the object.

**Activity labels.** With no tool card, the line beside the avatar is the *only* feedback
during a turn, and the client derives it from `currentActivity.tool` through its own table:
`WebSearch` → "Searching the web", `Read`/`BoxRead` → "Reading file", `Shell`/`BoxShell` →
"Running commands" (with a `detail` → "Drafting the file"), `Task` → "Waiting on another
agent", `SendToAgent` → "Messaging <name>", `Screenshot`/`Computer`/`request_box_help` → "On
its computer", anything starting `browser_` → "Browsing the web", everything else → "Working".

Ours mapped `browser_navigate` and `browser_take_screenshot` onto `WebFetch`, which reads
"Reading the web" while the agent is clicking around a page — passing the real name through
hits the `browser_` branch instead. The map now also covers the shell, file, subagent and MCP
tools, which all previously fell through to a bare "Working".

## 2t. The app looked dead, and the browser looked broken — two separate causes

Both were reported as "the browser doesn't work". Neither was the browser.

### The turn never ended

### The VNC pane was empty while the screenshots were correct

```

xwininfo -id 0x801952      →  Map State: IsUnMapped
```

## 2u. Remote image URLs do not render — which is why the original attaches instead — DONE

Asked to "extract some images", the model answered with `[Xem ảnh](https://…)` links. Markdown
image syntax would seem like the fix, and the renderer really does handle it — `img({node, src})`
routes to the same `Dj` component attachments use. But feeding it a real CDN URL renders

```
Couldn't load image i1-thethao.vnecdn.net
```

The client will not fetch a remote image. That is not a gap in our port: it explains the
original's behaviour. **Every image in the original's transcript is an attachment** — a
screenshot, or bytes staged through the gateway — never a link to a third-party host. Its
media path resolves a *path* through `readAttachmentImage` / `readAttachmentChunk`, and a
`https:` source has no such path.

So "show me the images on this page" has one correct implementation: fetch the bytes and stage
them as attachments, exactly like a screenshot. **Built** — `attach_image({url, alt})`, with
three pieces the feature does not work without:

**Measuring four formats, not one.** `stageImage()` read the PNG IHDR chunk and returned null
for anything else, and null there means the attachment is silently never posted — a JPEG from a
CDN produced no error, just nothing. `imageSize()` now covers PNG · JPEG · GIF · WebP. JPEG has
no fixed offset: the size lives in a start-of-frame segment behind however much EXIF and ICC the
camera wrote, so the segment chain has to be walked, skipping standalone markers and padding
`FF`s or the walk desynchronises. SOF4/SOF8/SOF12 are *not* frame headers, which is why the
marker ranges have holes. WebP stores its size three different ways (`VP8X` / `VP8 ` / `VP8L`)
and is worth handling because it is what image CDNs now serve by default.

**Mime and extension come from the bytes.** Both were being taken from the caller — the gateway
hardcodes `image/png` in the data URL prefix — and the renderer routes on the URL's extension
and decodes by mime, so a WebP named `.png` reaches the image component and fails there. A CDN
serving `photo.jpg` as WebP is ordinary, so the file name is not evidence.

**A fence, because the URL comes from the model.** This is a request-forgery surface reachable
from any page the agent reads. http(s) only; the hostname is *resolved* and every address
checked against loopback / RFC1918 / link-local (including `169.254.169.254`) / ULA, since
`evil.test` resolving to `127.0.0.1` is the ordinary attack; unresolvable counts as internal;
and `res.url` is re-checked after redirects, which the first check cannot see. The concrete
thing being protected is the box's Chrome DevTools port — unauthenticated RCE on loopback.

Measured (`scripts/e2e-attach-image.mjs`, 14/14): JPEG 300×200, WebP 550×368, GIF 400×400 all
attach, read back through `readAttachmentImage` with correct dimensions and mime; all five
blocked URLs refused. End to end in a live turn — "open the Cat article and show me 2 images" —
`browser_navigate` → `browser_evaluate` → `attach_image` ×2, and **zero** markdown links.

## 2w. Presence never animates — SOLVED: the channel name was wrong

**Root cause: we broadcast on `channel: "roster"`, and there is no such channel.**

The SSE frame never reached the renderer. The coordinator process — not the renderer — decodes
the stream, looks the channel up in its own table, and drops anything missing from it:

```js
const family = coordinatorEventFamilyForSseChannel(event.channel);
if (family == null) return;          // silent: no log, no error, no throw
```

`SSE_CHANNEL_BY_FAMILY` lists exactly: `transcript` · `agents` · `agent-upserted` · `tray` ·
`workflows` · `subagents` · `async-tasks` · `automations` · `mcp-servers` · `forever-box` ·
`teach-recording` · `box-disk-pressure` · `computer-action` · `outline` · `sharing` ·
`host-settings`. **`roster` is not one of them.** Roster changes go out as `agent-upserted`
(one changed agent) or `agents` (the whole list), and the coordinator forwards them to the
renderer as `{kind, event: payload}`.

Fixed by renaming the channel. Measured immediately after:

* a bot created through the gateway appears in the sidebar in **~1.5s, no reload** (was: still
  absent after 12s);
* the avatar animates while a turn runs — ten distinct screenshot hashes across a turn, where
  before every sample was byte-identical.

### Why it took six wrong fixes first

Everything ruled out below was ruled out correctly — and none of it mattered, because the
payload was never looked at. Each "fix" was a better-shaped envelope posted to an address that
does not exist.

| Hypothesis | Test | Result |
|---|---|---|
| Sampling the wrong element | hash sidebar row, header and transcript strip together | all three identical |
| Background-window throttling | `bringToFront()`, assert `visibilityState:visible`, `hasFocus:true` | still identical |
| Missing `snapshotEpoch` | added `snapshotEpoch`/`snapshotSeq` to every row | no change |
| Incomplete row schema | filled all 16 validated fields (was sending 5) | no change |
| Missing `isRunningTurn` | added (`Bon(n) = n.isRunningTurn ?? n.isRunning`) | no change |
| Wrong event shape | tried enveloped and wholesale, then both | no change |

The lesson is about *where* the reading was done, not how carefully. Six rounds went into the
renderer bundle, reasoning about how it consumes an event — while the frame was being discarded
one process earlier, by a table that is three lines long. When a payload change produces no
effect at all, stop refining the payload and prove the message is being delivered.

The row-schema and `snapshotEpoch` changes stay: the client's own validator requires them, and
they were verified against it. They just were not the cause.

### Still worth doing, found in the same table
We use two of the sixteen channels. `forever-box` would push computer-pane status instead of
waiting for the client's poll (visible as a lag before the Computer button appears), and
`subagents`, `outline`, `automations`, `host-settings` and `tray` are all pushable too.

## 2aa. Streaming: ours works, the pool's does not

Reported as "the answer arrives in one lump, there is no streaming". Measured on both sides
rather than reasoned about, because `chat.ts` does call `streamPool` and "it calls the streaming
function" proves nothing — the same trap as `web_fetch` reporting `status=done` for a page it
never read.

**Our backend streams.** Sampling the transcript every 250 ms, the reply grows in place:

```
t+0.3s   len=0      streaming=true
t+20.9s  len=43     streaming=true
t+21.2s  len=111
t+21.5s  len=227
…16 growth steps…
t+24.1s  len=1206
```

**The pool does not.** Calling `/v1/chat/completions` with `stream:true` directly, no backend
involved:

```
HTTP 200 · first content at 8860ms · 3 chunks · 9.3s total
```

Three chunks, the first at 95% of the total time. The route accepts `stream:true` and answers
with an SSE-shaped body, but the content is buffered upstream and flushed near the end. So the
visible behaviour — a long silence, then the text appearing almost at once — is the pool's
shape, faithfully relayed.

Nothing to fix in this backend. What would change the experience is upstream (a pool route that
forwards tokens as they arrive); what we can do meanwhile is make the wait legible, which the
"Thinking" indicator now does since §2w.

## 2ab. A pool outage left the bot spinning forever

Reported as two separate bugs — "a new bot gives no reply" and "the bot spins forever" — and
they turned out to be one upstream failure plus one defect of ours.

**Upstream.** The model pool stopped answering completions. Its own pages still served in
86–239ms (`GET /v1/docs`, `/health`, `/` all 200), and the key is accepted, but
`POST /v1/claude` and `POST /v1/chat/completions` both time out. Nothing to fix locally; the
turn simply produces nothing until it recovers.

**Ours.** `runTurn`'s `!r.ok` branch wrote the error into the bubble, cleared `streaming`, and
returned — without clearing presence. Every other exit from that function clears it; this was
the one that did not, and it is the branch an outage takes. Measured against a dead pool:
`isRunning=true`, `currentActivity={"kind":"thinking"}` still set 20 seconds after the bubble
already read `[grokbot2] Pool error: …`. One line, `clearPresence(agentId)`.

**The test lied first, and that is the part worth keeping.** `scripts/e2e-pool-failure.mjs`
passed with the fix deliberately removed. The cause was Windows process handling: `spawn(…,
{shell: true})` puts `cmd.exe` between the script and `tsx`, so `child.kill()` killed the
wrapper and left the backend listening on 8799. Every later run reused that stale process —
still running the *fixed* build — so the test was measuring code that was no longer on disk.
It now refuses to start when the port is already answering, and kills the tree with
`taskkill /T /F`. Proven both ways afterwards: 4/4 with the fix, 2/4 without
(`isRunning=true`, `activity={"kind":"thinking"}`).

Also fixed while in here: an SSE drop is not fatal. The client reconnects on its own in ~5s and
survives outages of at least 120s — measured with `/gw/__dropsse`, a diagnostic route that cuts
the stream while the server keeps answering. Killing the backend cannot answer that question,
because it removes the retry target at the same moment.

## 2ac. The transcript froze because our sequence numbers had gaps

The reported symptoms were three, and they were one bug: a bubble stuck at "Để" while the
backend held 1118 characters; a finished reply that only appeared minutes later; and a sidebar
preview that was always correct while the conversation pane was not.

**How the client consumes events.** There is no EventSource and no WebSocket — the coordinator
reads SSE off a `fetch` body itself, and every domain keeps an *ordered replica* keyed by
`"roster"` or `` `transcript:${agentId}` ``, with an epoch and a sequence. The accept rule is
strict:

```js
if (t.sequence === this.acceptedSequence + 1) { this.value = applyEvent(…); this.acceptedSequence = t.sequence; this.drainBuffer(); return }
this.bufferBounded(t.sequence, e.event);   // a gap parks the event in a bounded buffer…
this.startAttempt();                       // …and asks for a resync
```

**What we sent.** `orderedFor(agentId, last.seq)` — the entry's **global** sequence, shared by
every agent. So any other bot writing an entry put a hole in this bot's replica. Measured on the
wire with two bots writing alternately: `1064, 1068, 1072, 1076` — a gap of four before every
single event. Only the first event of a turn was ever applied live.

The roster never had this bug because it always used its own counter (`++rosterSeq`). Same push,
same connection, two different sequence sources — which is exactly why the preview updated while
the bubble stood still. That asymmetry was the clue that named the cause.

Fixed by counting **pushes per agent** (`nextTranscriptOrdered`), not entries. A streamed reply
emits many events for one entry and each is an event the replica counts, so the counter advances
per push. Measured after: `transcript:agent-170 → 1,2,3,4,5,6` and `transcript:agent-171 →
1,2,3,4`, both starting at 1. `scripts/e2e-ordered-sequence.mjs` reads the raw frames and
asserts contiguity; it fails 3/5 when the global sequence is put back, so it can actually catch
the regression. It needs no model, so it runs while the pool is down.

**A snapshot on reconnect turned out NOT to be needed**, which was the plan going in. The client
resyncs itself: it derives an anchor from the `ordered` envelopes we already send
(`observedAnchor = {epoch, sequence}`), refetches through the ordinary transcript method, and
installs `coverage: {kind: "transcript-live-range", fromSequence, throughSequence}`. That path
was working all along — it just re-broke on the very next event, because the next event had a
gap too. Fix the numbering and the built-in recovery does the rest.

**One dead frame removed.** The connect-time snapshot was sent on `channel: "roster"`. "roster"
is the replica KEY, not one of the sixteen channel names the coordinator forwards, so the frame
was dropped silently — the same trap as the presence bug, in the code written to fix the
presence bug. It goes out on `agents` now, deliberately without `ordered`, because the client
reads a missing envelope as "replace wholesale" and that is what a fresh connection wants.

## 2ad. The computer pane is pushed now, not polled

`forever-box` is the third of the sixteen SSE channels we use (after `transcript` and
`agents`/`agent-upserted`), and the only one the coordinator treats specially: it runs
`proxifyForeverBoxStatus(payload, vncProxy)` on the way past, rewriting `vncUrl` and any
`windows[].vncUrl` through the VNC proxy. So the payload must BE the status object, not a
wrapper — and `foreverBoxStatus()` already returns exactly that, `agentId` included. The
renderer files it by that field: `ingestForeverBox: I => { const P = m(I.agentId); … }`, so a
frame without it lands under `undefined` and the pane never leaves "off".

Fired on transitions only, from three points in `forever-box.ts`: taking the computer, the
release after the grace period, and a handoff appearing or clearing. `beginComputerUse` runs on
**every** browser action, so it announces only the off → running edge — 5 repeat calls put 0
extra frames on the wire (measured). Cancelling a pending release is not a change either: the
status was "running" throughout the countdown.

`scripts/e2e-box-push.mjs` reads the raw frames — 6/6, no model and no window needed, so it runs
while the pool is down.

**A leak found by the test, then fixed.** The release timer is armed by the end of a *turn*
(`clearPresence → endComputerUse`), but the session is *started* by `ensureForeverBox`, which the
client calls when the user opens the pane. Opening a pane is not a turn, so an idle bot the user
glanced at reported `running` until its next turn finished — the §2z symptom (an idle bot showing
a live screen) reached from the other side. The first version of this test hit exactly that and
sat out the grace period waiting for a release nothing had armed.

The obvious fix — stop claiming `running` — is wrong, and the client says why. Its placeholder
falls through to `emptyMessage ?? "Booting up the computer"` with a spinner, and `emptyMessage`
is a component prop no status reply can reach: answer `off` to an *ensure* and the pane spins for
ever. That is the hang `beginComputerUse` was added here to fix.

So the fix is to arm the release at the same moment: `beginComputerUse(id); endComputerUse(id)`.
Nothing else changes — any tool action cancels the timer (`beginComputerUse` clears it) and the
end of a turn re-arms it. It cannot be pushed out indefinitely by the client either, because
`ensureForeverBox` fires on open/focus/reconnect while the *poll* is `getForeverBoxStatus`.
Measured 9/9, and 7/9 with the one call removed — the case fails for the right reason
("still running — nothing armed the release").

## 2ae. A message arriving mid-turn swallowed the tool call

Seen in a real multi-agent run: Frontend Dev's transcript held a 28,146-character bubble whose
text ended in a complete, valid `TOOL_CALL: edit_file_v2({"relative_workspace_path":"index.html",
…})` that never executed. The file was never written and the user was shown the machine line.

The parser was innocent, and checking that first is what kept this from being a guess: the exact
28k string matches `parseToolCall`'s regex in 0ms and yields `edit_file_v2`, which is registered
and runs correctly when invoked directly (pending card, then done). What actually gave it away was
the entry two rows earlier — an **empty** bubble, immediately followed by an inbound message. That
is the fingerprint of an aborted turn:

```
sendPrompt → inflight.get(agentId)?.abort()        // a new message kills the running turn
runTurn    → if (controller.signal.aborted) return;   // returns BEFORE tidying and BEFORE parsing
```

In a multi-agent conversation a peer writing to a bot mid-turn is the normal case, not an edge
case, so this fires constantly. The early return left an empty bubble sitting for ever when
nothing had been produced, and a finished answer with its `TOOL_CALL:` line exposed when the
non-streaming fallback had already revealed the whole text.

The abort path now tidies up: strip the machine line, keep what was said, and remove the bubble
entirely if nothing was said. The tool is **not** run — the turn was abandoned because someone
moved on, and acting on a superseded decision is worse than dropping it.

`scripts/e2e-abort-swallows-tool.mjs` reproduces it by sending a second message three seconds
into a tool-bound turn: 1/2 before the fix (`1 empty bubble(s)`), 2/2 after.
